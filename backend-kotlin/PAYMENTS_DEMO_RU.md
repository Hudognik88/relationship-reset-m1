# Демо-оплата Prodamus: границы и запуск

Эта версия добавляет серверный заказ и обработку подписанного уведомления.
В исходной конфигурации оплата **отключена**. Compose получает режим из закрытого
файла без ключа; переход в demo выполняется отдельной командой со скрытым вводом.
Рабочие платежи и публичная продажа не включаются.
Существующая репетиция по приглашению продолжает работать без оплаты.

**Проверка версии провайдера обязательна.** Публичная страница продавца сейчас
выглядит как новый Prodamus.Pay (PF2). Его актуальная документация описывает
UUID для `order_id`, но не описывает `demo_mode` в checkout/webhook.
Поэтому нельзя считать параметр `demo_mode=1` доказательством отсутствия
списания на PF2. До подтверждения тестового режима именно этого канала
оставляйте сервер в `disabled` и не запускайте checkout. Поддержка UUID
подготовлена, но не доказывает полную совместимость PF2.

## Что проверяет реализация

Клиент сохраняет вымышленную анкету и личный ключ кабинета. Заказ привязывается
к постоянному владельцу кабинета и конкретной анкете. Сервер задаёт продукт
`pilot_7d`, сумму 99000 копеек, RUB и режим demo. Сумма из браузера не принимается.
Повтор запроса с тем же UUID возвращает тот же заказ; другой UUID для той же
анкеты сохраняется как его псевдоним. Использовать UUID для другой анкеты нельзя.

Подписанная ссылка указывает только на `https://relationshipreset.payform.ru/`
и содержит `demo_mode=1`. Контакты, содержание анкеты, ключ кабинета и cookie
в неё не попадают. Открытие ссылки производится клиентом явно.

Возврат со страницы оплаты не меняет заказ. Только серверное уведомление
с корректным `Sign`, ожидаемыми доменом, суммой, валютой, номером заказа,
статусом `success` и явным `demo_mode=1` создаёт демо-доступ на семь дней.
Запись уведомления, изменение заказа и выдача доступа — одна транзакция.
Повторная доставка не продлевает срок и не выдаёт второй доступ.

Удалённая анкета не заменяется новой в старом заказе. Успешное уведомление
после удаления получает состояние `review_required`, без выдачи доступа.
Удаление после выдачи делает доступ неактивным; платёжный журнал сохраняется.
Сервер не возвращает ссылку на оплату заказа удалённой анкеты.
Демо-доступ пока не ограничивает существующую бесплатную репетицию.

## API

| Метод и путь | Условия и результат |
| --- | --- |
| `GET /client/orders` | Cookie клиента; собственный заказ и демо-доступ. При отключённой оплате `enabled:false`, остальные поля null. |
| `POST /client/orders` | Cookie, точный Origin, CSRF; JSON `synthetic:true`, `product:"pilot_7d"`, `client_request_id` UUID, `case_id` 32 hex. При отключённой оплате 503. |
| `POST /payments/prodamus/webhook` | HTTPS, без query; подпись в единственном заголовке `Sign`; URL-encoded или multipart form, до 64 KiB. При отключённой оплате 503. |

В уведомлении `order_num` — наш идентификатор `rrstg_…`, а `order_id` —
идентификатор Prodamus: числовой PF1 либо UUID PF2. UUID приводится к нижнему
регистру после проверки подписи. JSON-уведомления и подпись в теле не поддерживаются.
Успешный ответ 200 выдаётся после фиксации транзакции. Неподписанное,
несовпадающее или неявно тестовое уведомление не выдаёт доступ.
Сырой webhook, контакты плательщика и подпись не сохраняются.

## Контролируемое обновление VPS

Миграция `004_client_payments.sql` добавляет `rr_client_orders`,
`rr_client_order_requests`, `rr_payment_receipts`, `rr_client_entitlements`.
Старые миграции 001–003 неизменны. Обычный автодеплой не применяет новую схему.

После полного успешного push CI для точного SHA загрузите
`scripts/upgrade-payments-vps.py` из этого же коммита, проверьте SHA-256
и запустите отдельным процессом от root:

```sh
python3 upgrade-payments-vps.py FULL_VERIFIED_COMMIT_SHA
```

Установщик принимает проверенный baseline
`fd557872d05659dad97b3ccd8cf969291c0f0e86`, сохраняет приватную контрольную
копию, применяет только дополнительную миграцию и обновляет контейнер API/Caddy.
После него проверяются прежний API, кабинет клиента, панель владельца,
отключённые платежи и восстановление 15 таблиц из закрытой резервной копии.
При сбое возвращается прежний образ и конфигурация; живая БД не затирается.

## Подключение закрытой конфигурации к VPS

На сервере с проверенным baseline
`345b317511e22f56c3f0e6b3c21e7f3b1c2d2457` сначала выполните
`scripts/upgrade-demo-config-vps.py FULL_VERIFIED_COMMIT_SHA` из нового
проверенного коммита после успешного полного CI. Сначала сверьте SHA-256 файла.
Этот отдельный установщик добавляет только закрытый файл и его read-only mount,
не применяет новых миграций и проверяет backup/restore прежних 15 таблиц.
Новая конфигурация содержит только `version:1` и `mode:disabled`.

Compose передаёт `RR_PRODAMUS_CONFIG_FILE=/run/secrets/prodamus_demo`.
Сам файл находится в `.secrets/prodamus-demo.json`: root-owned, режим 0444,
родительский каталог 0700. Это нужно для непривилегированного пользователя
внутри контейнера. Формат `.env` остаётся прежним: только домен и номер релиза.

## Включение только demo

Сначала подготовьте настройки в собственном кабинете Prodamus, не пересылая
секрет в чат или GitHub. В PF2 это «Каналы продаж → нужный канал → Интеграции»;
ключ создаётся отдельно и показывается один раз. Создание ключа выполняет
владелец. Действующий ключ нельзя заменять без проверки других интеграций.

Команду `enable` выполняйте только после подтверждения тестового режима
канала со стороны Prodamus. После установки конфигурационного обновления в
терминале VPS от root доступны команды:

```sh
python3 /opt/relationship-reset-kotlin-deployer/configure-prodamus-demo-vps.py status
python3 /opt/relationship-reset-kotlin-deployer/configure-prodamus-demo-vps.py enable
# При необходимости вернуть отключённый режим:
python3 /opt/relationship-reset-kotlin-deployer/configure-prodamus-demo-vps.py disable
```

Команда `enable` дважды запросит секрет со скрытым вводом. Не передавайте его
аргументом команды или через переменную окружения. Необязательный `--sys`
предназначен только для выданного Prodamus идентификатора интеграции.
Скрипт приостанавливает автодеплой, сохраняет закрытую контрольную копию,
атомарно записывает файл, пересоздаёт API и выполняет проверки. При сбое
возвращает прежний файл и контейнер. Пересоздание обязательно: обычный restart
после атомарной замены может оставить старый inode файла в bind mount.

`status` показывает только режим. Значение ключа и его хеш не выводятся.
Проверки используют прежние вымышленные анкеты; заказ или оплата у провайдера
этими командами не создаются. При незавершённой ручной операции автодеплой
останавливает новые обновления до восстановления её состояния.

Для локальных проверок без Compose также сохранён прежний контракт:

| Настройка приложения | Требование |
| --- | --- |
| `RR_PRODAMUS_MODE` | `demo`; значение `live` отклоняется при запуске |
| `RR_PRODAMUS_SECRET_FILE` | Путь к закрытому файлу внутри контейнера |
| `RR_PRODAMUS_FORM_URL` | Необязательно; допускается только `https://relationshipreset.payform.ru/` |
| `RR_PRODAMUS_SYS` | Необязательно, только выданный Prodamus идентификатор интеграции |

Не смешивайте этот контракт с `RR_PRODAMUS_CONFIG_FILE`.
Не передавайте секрет через `RR_PRODAMUS_SECRET`: такой запуск отклоняется.
Адрес уведомления для нашей интеграции:
`https://api-staging.poslessory.ru/payments/prodamus/webhook`.
В PF2 настройки находятся в канале продаж: «Уведомления → Уведомления о
разовых оплатах», событие «Заказ оплачен». Существующие рабочие получатели
должны сохраниться. Возможность добавить отдельный URL надо проверить в
кабинете. PF2 учитывает `urlNotification` при включённых уведомлениях канала;
прежняя PF1-инструкция ограничивала его наличием `sys`. Текущий код сохраняет
консервативное условие `sys` и предполагает явную настройку URL в кабинете.

Прежде чем включать demo, подтвердите режим подписи и форму уведомления
именно для PF2-канала. Текущая версия использует заданный секрет без
автоматического добавления `demo` и требует `demo_mode=1` в уведомлении.
Эта схема описана для PF1; для PF2 её поддержка пока не подтверждена.
Не устраняйте несовпадение отключением проверки подписи или признака demo.
Тестовые карты из справочника PF1 до такого подтверждения не используйте.

Затем выполните один полный сценарий с вымышленной анкетой и тестовой оплатой
Prodamus: заказ → checkout → настоящий подписанный callback → один доступ →
повторный вход. Проверки CI с синтетически подписанными уведомлениями этого
сценария у провайдера не заменяют. Реальные списания не выполняются.

## Проверки и источники протокола

`ProdamusContractTest` проверяет парсинг форм и HMAC; `PaymentRoutesTest` —
авторизацию/CSRF/подпись и выключенный режим; `PaymentStoreIntegrationTest`
на одноразовом MySQL — владельца, повторы, гонки, удаление и атомарный откат.
`smoke-payments-vps.py --expect-mode disabled|demo` проверяет ожидаемый режим
и номер релиза. В demo он требует отказ 401 на неподписанный webhook,
в disabled — отказ 503; анонимный доступ к заказам всегда запрещён.
Это проверка обработчика, а не подтверждение корректности введённого ключа.

- https://help.prodamuspay.ru/kanaly-prodazh/integracii/kak-sozdat-sekretnyi-klyuch-dlya-podklyucheniya-integracii

сценария на рабочем домене. Этот релиз не заявляет их готовность.
